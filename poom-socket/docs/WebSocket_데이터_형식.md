# 음성 비서를 위한 WebSocket 


| 구분 | 저장/전달 위치 | 형식 |
|------|----------------|------|
| **사용자 음성 (입력)** | 클라이언트 → 서버 **Binary** 메시지 전체 | PCM. JSON 필드 없음. |
| **사용자 발화 텍스트** | 서버 → 클라이언트 **Text** 메시지 안의 **user_text** | JSON |
| **AI 음성 (출력)** | 서버 → 클라이언트 **Binary** 메시지 전체 | PCM. JSON 아님. |
| **AI 답변 텍스트** | 서버 → 클라이언트 **Text** 메시지 안의 **ai_text** | JSON |

- **JSON 형식을 직접 확인**하려면: 브라우저에서 **http://localhost:8765/docs/ws-inspect** 로 접속한 뒤 "연결 후 로그 보기"로 WebSocket을 연결하면, 서버가 보내는 메시지(Binary = ai_voice, Text = user_text/ai_text JSON)가 실시간으로 표시된다.

---

## 데이터 흐름

- **REST**는 Swagger(OpenAPI)로 문서화하지만, **WebSocket**은 요청/응답 구조가 달라 Swagger에 메시지 흐름을 넣기 어렵다.
- 이 서버에서는 다음으로 처리한다.
  1. **GET /api/voice/ws-spec**  
     WebSocket 프로토콜 스펙 + **필드 매핑** + **출력 JSON 예시**를 JSON으로 반환. Swagger UI에서 호출 가능.
  2. **GET /docs/ws-inspect**  
     필드 매핑 표 + **수신 메시지 로그**를 보여주는 페이지. 연결 후 오는 Binary/Text(JSON)를 **직접 확인** 가능.
  3. **마크다운 문서**  
     `docs/WebSocket_데이터_형식.md`, `docs/프론트_음성재생_가이드.md` 에 상세 내용 정리.

---

## 흐름 요약

```
[클라이언트]  마이크 캡처 → PCM 바이너리 → WebSocket 전송
                    ↓
[서버]        수신 PCM → Gemini Live API (음성→음성) → 응답 PCM
                    ↓
[클라이언트]  WebSocket 수신 → PCM 바이너리 → 스피커 재생
```

---

## 입력 (클라이언트 → 서버)

| 항목 | 값 |
|------|-----|
| **메시지 타입** | **Binary** (WebSocket binary frame) |
| **포맷** | Raw PCM, **필드/JSON은 따로 없음** (바이트 배열만) |
| **샘플 레이트** | 16 000 Hz |
| **채널** | 1 (모노) |
| **비트 깊이** | 16bit signed integer, Little Endian |
| **바이트 수** | 1샘플 = 2바이트, N샘플 = 2N 바이트 |

- 한 번에 보내는 길이는 자유(예: 20ms 단위 등). 서버는 들어오는 바이너리를 그대로 16kHz 모노 PCM으로 해석함.

---

## 출력 (서버 → 클라이언트)

| 항목 | 값 |
|------|-----|
| **메시지 타입** | **Binary** (WebSocket binary frame) |
| **포맷** | Raw PCM, **필드/JSON 없음** (바이트 배열만) |
| **샘플 레이트** | 24 000 Hz |
| **채널** | 1 (모노) |
| **비트 깊이** | 16bit signed integer, Little Endian |
| **바이트 수** | 1샘플 = 2바이트, N샘플 = 2N 바이트 |

- 여러 청크로 나눠서 보냄. 클라이언트는 수신한 청크를 **스케줄 재생**으로 이어서 재생해야 함.

---

## 필드가 없는 이유

- 프로토콜이 **Raw PCM 스트리밍**이라, 헤더/JSON 없이 **순수 오디오 바이트**만 전송함.
- 인코딩/메타데이터는 고정(위 표 참고). 별도 필드로 “sampleRate”, “channels” 등을 보내지 않음.

---

## 클라이언트 처리 요약

1. **송신:** 마이크 → 16kHz 모노 16bit PCM으로 변환 → WebSocket **binary**로 전송.
2. **수신:** WebSocket **binary** 수신 → 24kHz 모노 16bit PCM으로 해석 → 스케줄 재생으로 이어서 재생.

(스케줄 재생은 `docs/음성재생_가이드.md` 참고.)

---

## 말풍선(텍스트) 지원 시 – 프론트에서 다룰 데이터 

말풍선에 **사용자 발화 텍스트**와 **AI 답변 텍스트**를 보여주려면, 서버가 텍스트를 별도로 보내줘야 한다.  
프론트는 아래 **세 가지**를 구분해서 처리하면 된다.

| 용도 | 키/이름 | 전송 방식 | 데이터 형식 |
|------|---------|-----------|-------------|
| 사용자 발화 저장·표시 | `user_text` | WebSocket **텍스트** | JSON |
| AI 답변 텍스트 표시 | `ai_text` | WebSocket **텍스트** | JSON |
| AI 음성 재생 | (이름 없음) | WebSocket **바이너리** | Raw PCM (JSON 아님) |

- **`user_text`**, **`ai_text`** → 서버가 **텍스트 프레임**으로 보낼 때 **JSON** 한 번씩.
- **AI 음성** → 기존처럼 **바이너리** 메시지. JSON에 넣지 않음.

### 서버 → 클라이언트 메시지 종류

1. **텍스트 메시지 (JSON)** – 말풍선용  
   - 사용자 발화(전사) 한 번 올 때:
     ```json
     { "user_text": "오늘 기분이 어때?" }
     ```
   - AI 답변 텍스트 한 번 올 때 (스트리밍이면 누적/갱신 방식은 정책에 따름):
     ```json
     { "ai_text": "저도 좋아요. 무엇을 도와드릴까요?" }
     ```
   - 둘 다 올 수 있는 형태로 가면:
     ```json
     { "user_text": "오늘 기분이 어때?", "ai_text": null }
     ```
     ```json
     { "user_text": null, "ai_text": "저도 좋아요." }
     ```
   - 프론트: `user_text` 있으면 사용자 말풍선, `ai_text` 있으면 AI 말풍선에 반영.

2. **바이너리 메시지** – AI 음성 재생용  
   - 형식은 위 “출력 (서버 → 클라이언트)”와 동일 (24kHz 모노 16bit PCM).  
   - 이걸 **ai_voice**처럼 “AI 음성 재생용 데이터”로만 쓰면 됨. JSON 필드가 아님.

### 정리
  - **user_text** (사용자 발화 저장/표시) → JSON 텍스트 메시지
  - **ai_text** (AI 답변 표시) → JSON 텍스트 메시지  
  - **ai_voice** (AI 음성 재생) → **JSON이 아니라** WebSocket **바이너리** (PCM)
